# S5.5a 最终制品性能与资源基线

## 结论

S5.5a 已完成最终制品的逐 Pod 时间线、trace-on/off、worker/embedded 和 1/5/20 Pod 资源
A/B；独立 reviewer 终审 `PASS`（P0/P1/P2=0）。普通 OCI 冷启动尚未达到 S5.5f
门禁：worker 串行 `PodScheduled→Ready` nearest-rank P95 为 1965.379ms，5×10 并发为
2899.045ms。问题已经被分成三个后续优化域：S5.5b 的跨 Pod 锁、S5.5c 的外部网络命令、
S5.5d/e 的持久化和 Guest cold boot。

worker 拆分没有造成启动劣化：同一最终制品的 trace-off 串行 P95，worker 为 1964.469ms，
embedded 为 2001.555ms，worker 快约 37.1ms。worker 的稳态 Pod cgroup 比 embedded 增加约
4.6MiB/Pod，并增加 3 个 Host PID；这是隔离 VMM/vCPU/virtiofs/Guest memory 的明确成本，
不回退 S5.4 已验收的进程边界。

GLM 在 W1 执行的全量 Node E2E 是独立并行验证，不进入 S5.5a 状态。S5.5 主线只使用 W2
及控制节点，未访问或修改 W1。

## 测量口径

- 启动延迟使用同一 observer 的 host monotonic clock；门禁分位数为 nearest-rank。runner
  自带的线性插值分位数只保留作原始输出，不用于验收。
- RunPodSandbox 使用 containerd receive/return 日志按 Pod UID 和 sandbox ID 重建；CubeShim、
  Cubelet、CNI 和 worker trace 使用同一 operation ID，并写入独立日志。
- trace-on 和 trace-off 均为串行 50 次及 5 轮×10 并发，固定节点、镜像 digest 和成功率
  100%；不得用限流或轮均值隐藏排队。
- 资源 A/B 在 Ready、稳定 10 秒、稳定 30 秒三个时间点采集；worker 与 embedded 都执行
  1/5/20 Pod×3 轮，顺序固定，使用自然 page cache，不执行 drop-cache。
- 进程 PSS 和 cgroup memory 是两套独立账本，不能相加。节点 `MemAvailable` 易受缓存影响，
  只作辅助，不直接作为 `RuntimeClass.overhead`。

## 正式制品内存拆账

`inv-98cji3g3ms` 保存完整 `/proc/<pid>/smaps`、`smaps_rollup`、maps、线程、cgroup 与节点
meminfo。Guest RAM 由唯一的 524288KiB 匿名 VMA 识别；该 VMA 的 Size 是 Guest address
space 上限，不是 Host 实际常驻量，本次 PSS 为 96256KiB。

进程 PSS 账本（可加总）为：Guest RAM 96256KiB、worker residual 3772KiB、worker 共享文件
映射 20886KiB、Shim 12537KiB；合计 133451KiB。`worker residual` 明确包含 VMM heap 和
进程内 virtiofs，smaps 本身不能继续精确拆分。

cgroup 账本单独保存 `anon/file/shmem/kernel/memory.current/memory.peak`。它与 PSS 的共享页、
shmem 口径可能重叠，禁止把两个账本相加。为估算 virtiofs resident 增量，另用未合入生产
分支的诊断 commit `19dcc33da1c6a113f66a5b96797a79704d5d2518` 做 0/1/2 device A/B；
最终结果见下一节。

## virtiofs resident 增量估计

诊断制品 bundle SHA-256 为
`9b128b789d85e6ea8db6ca20026a55a7ebe2aed6f8b8dc1e9351f250689df91b`，只允许改变
`cube.s55a.diag.virtiofs_devices=0|1|2`。Kubernetes 为每轮创建 managed Pod sandbox；容器
使用节点上不存在的 image 且 `imagePullPolicy: Never`，所以三档都只运行相同 sandbox
lifecycle，不引入 Guest 容器工作集。三档各三轮，按 Latin-square 顺序
`0,1,2 / 1,2,0 / 2,0,1`，每次稳定 30 秒。执行编号为 W2 `inv-68cks7gqhw`、控制节点
`inv-v8cks80cnf`，9/9 成功且每轮后 exact-zero。

| 独立账本指标 | `1−0` 配对均值（95% CI） | `2−1` 配对均值（95% CI） |
|---|---:|---:|
| worker 非 Guest PSS | +283.3KiB（+158.4～+408.3） | +22.7KiB（−176.4～+221.7） |
| worker residual PSS | +56.0KiB（+46.1～+65.9） | +53.3KiB（+41.9～+64.8） |
| Pod leaf `memory.current` | +145.3KiB（+85.4～+205.2） | +160.0KiB（−28.8～+348.8） |
| Pod leaf kernel memory | +85.3KiB（+50.4～+120.2） | +90.7KiB（+79.2～+102.1） |

Guest RAM VMA 九次都严格为 524288KiB，实际 PSS 九次都为 94208KiB；因此配对差值没有被
Guest 工作集变化污染。第一个设备的 worker 非 Guest PSS 增量有明确正区间；第二个设备的
同指标 CI 跨 0，不能声称存在稳定的额外 PSS 成本。cgroup 与 PSS 是独立口径，表中数值禁止
相加。该结果只称为 virtiofs resident 增量估计，不包装成 allocator 精确值，也不能由此把
约 100MiB/Pod 的主要常驻量归因给 virtiofs。

## 测试与无效探针

- Cubelet：`go test -race ./services/runtime/... ./plugins/cube/runtime_resource/...` 全部通过。
- CubeShim：单线程完整库测试 294/294 Passed。并行运行有一个使用进程级 FD table 的用例与
  其他用例互相干扰；该用例单独通过，完整单线程测试通过，因此记录为测试工具限制。
- 第一批 Go 测试因只读 cache 或运行环境拒绝 `SO_PASSCRED` 而无效；正式结果使用独立可写
  cache 且支持 Unix credential socket option 的运行。
- 第一版诊断用 `crictl runp` 和 `system.slice` 直接创建 sandbox；worker 后端还要求 managed
  Pod placement，因此该请求实际选择 embedded VMM，不能用于生产 worker 归因。两个失败尝试
  分别保存在 `failed-attempt-inv-98ck9mggg6` 和 `failed-attempt-inv-b8ckbt0iwp`，没有删除或
  混入正式 9 个样本。正式实验改由 Kubernetes 生成 `kubepods` cgroup 后通过。
- worker 资源矩阵 `inv-38cj760spu` 与 embedded 矩阵 `inv-88cjsd045h` 的 W2 数据均 9/9
  成功且最终资源归零。两次控制端都在删除最后一个 namespace 后因 HTTP marker server
  退出竞态漏读最后一个 zero marker；这是测试协调问题，不是 workload 或清理失败。可复用
  脚本已改为只把 HTTP 200 视为最终确认，正式清理使用独立 exact-zero。
- 恢复生产制品为 `inv-a8cm3egxjv`；W2 最终 exact-zero `inv-08cm4gg07f` 的 sandbox、worker、
  Shim、VM、lifecycle、cleanup job、adapter、reaper、shared、TAP、mount 和 active lease 全为
  0，且生产 Shim/worker SHA-256 精确匹配。控制端首轮 `inv-b8cm4gg0ew` 只因 GLM 正在使用的
  W1 为 NotReady 而失败；W2 当时及之后均为 Ready。按资源隔离边界，最终
  `inv-a8cm6pgic4` 以本阶段目标 W2 为 Ready 门禁，得到 0 S5.5 namespace、0 Cube Pod、W2
  Ready；它同时原样记录全集群另有 1 个 GLM-owned NotReady 节点，未触碰 W1。

# S5.5b 跨 Sandbox 并发与门禁证据

## 结论

S5.5b 实现 commit `3e827aaaae776fdbb297b99e69f4f9c61158b12f` 已把 RuntimeResource
adapter、Coordinator、Store 和 FD handoff Registry 的节点级大锁改为 per-sandbox 线性化。
实现专项和最终云端证据均由同一独立 reviewer 判定 `PASS`（P0/P1/P2=0），S5.5b 为
`DONE`。云端 race/unit/vet、串行与 5×10 并发、RuntimeResource restart、创建中取消及
exact-zero 均通过。

原方案给 S5.5b 同时设置的两个端到端检查点尚未达到：5×10 的
`CRI receive→start-vm` P95 为 995.585ms，五轮 VMM start 展开为 286.197～401.680ms。
直接负责本改动的 adapter lock-wait P95 已从 232.910ms 降至 5µs；剩余展开主要在连接
Shim 之前及后续网络命令/同步持久化路径。终审接受把 `CRI receive→start-vm≤450ms`
归入 S5.5c、在 S5.5d 进一步收紧到 300ms，并最迟在 S5.5d 重验 absolute VMM start
展开≤250ms。S5.5f 最终端到端门禁不变，因此这是责任边界修正，不是降低门禁。

GLM 的全量 Node E2E 在 W1 独立运行，不进入本阶段状态。本阶段只使用 W2
`ins-4dyul5ag` 和控制节点 `ins-qj8d7ypa`，未访问或修改 W1。

## 并发实现边界

- adapter、Coordinator、Store、FD Registry 只对同一个 sandbox 加 keyed lock；不同 sandbox
  的网络操作、F_DUP、持久化和 Release 可以真实重叠。
- `tapFiles` 与 Registry 内存 map 只在短临界区发布；OpenTap、Close、文件 I/O 和 persist
  不持有全局 map lock。Close 失败时保留 TAP ownership，重试成功后才删除。
- Store 的 token generator 只保留短 `generateMu`；生命周期记录仍采用临时文件、原子 rename
  和 parent fsync，不以关闭崩溃一致性换性能。
- 锁顺序为 `Coordinator[sid] → Registry[sid] → Store[sid]`，Acquire 路径为
  `Registry[sid] → Adapter[sid]`；专项 race 测试覆盖同 sandbox 线性化、跨 sandbox overlap、
  F_DUP/Release 竞态、List 的 rename/fsync 可见性和 commit-unknown 隔离。

## 残余并发展开

| 5×10 阶段 | P95 |
|---|---:|
| CRI receive→Shim connect | 597.526ms |
| Shim Create | 414.260ms |
| RuntimeResource | 138.400ms |
| adapter network prepare | 81.953ms |
| adapter/Store 单次原子记录 | 12.105/12.441ms |
| Shim Start | 1401.007ms |
| worker LaunchVmm | 1.658ms |
| start-vm→vsock ready | 1298.113ms |

提交一轮 10 Pod 本身只展开 37.602～43.259ms；到 Shim connect 时已经展开
218.006～378.988ms，到 start-vm 时为 286.197～401.680ms。S5.5a 五轮 start-vm 展开为
359.671、586.247、622.168、106.920、465.628ms；S5.5b 为 286.197、319.987、306.703、
401.680、309.662ms，均值从 428.127ms 降到 324.846ms，最大值从 622.168ms 降到
401.680ms，但仍未达到原 250ms 检查点。

containerd 在 CNI 完成后才连接 Shim，因此 receive→connect 的扩大是前置 CNI/CRI 排队的
直接上界；RuntimeResource 内部仍有 15 次外部网络命令/Pod 和五次原子状态提交。当前证据只
说明剩余时间位于这些边界，不把全部 receive→connect 时间武断归因给某一个 CNI 函数。
S5.5c 必须用进程内 netlink 关闭网络命令，S5.5d 再减少持久化与 placement 的同步等待。

## 生命周期与清理

- `inv-a8cp4bgud8`：5 个活跃 Pod 下重启 RuntimeResource，PID `4032858→89770`；重启前后
  都是 5 sandbox/5 worker，制品哈希不变。
- `inv-88cp4p0veu`：原 5 Pod 仍 Ready，重启后新增 5 Pod 也全部 Ready，随后正常删除。
- `inv-38cp6k08gn`：RuntimeResource 被 SIGSTOP 后创建 10 Pod，10/10 已调度且均处于
  Pending，再删除 namespace；`inv-88cp6x0n3p` 恢复服务，`inv-88cp79gnkw` 确认 namespace
  消失。120 秒自动恢复 timer 防止服务永久暂停。
- 重复 Release 的同 key 幂等、并发 Release 线性化和 commit-unknown 重试由固定候选制品的
  云端 `go test -race` 覆盖；生产清理随后未残留 active lease 或 reaper job。
- trace-off 恢复为 `inv-68cp87gx7f`。恢复后的 W2 exact-zero `inv-88cp8q0ni2` 得到 sandbox、
  Shim、worker、VMM、lifecycle、cleanup job、adapter、reaper、shared、TAP、mount 和 active
  lease 全部为 0；控制端 `inv-08cp8pg2rr` 得到 0 个 S5.5b namespace、目标 W2 上 0 个
  Cube Pod 且 W2 Ready。

失败记录没有删除或混入正式结果：`inv-98cp37gqfj` 仅因验收脚本假设了错误的 harness 路径，
没有执行 restart；`inv-68cp570cvi` 因前一轮已退出 CRI sandbox 尚未 GC 而在 SIGSTOP 前退出。
修正版分别使用 `/proc/MainPID/exe` 和活跃 worker/Shim/lease 前置条件。

## 原门禁状态与 Stage 归属决定

| 门禁 | 结果 | 状态 |
|---|---:|---|
| 同/跨 sandbox unit + race | 云端全部通过 | PASS |
| adapter lock-wait P95≤10ms | 0.005ms | PASS |
| 5×10 成功率 | 50/50 | PASS |
| 串行回退≤3% | Ready +0.33%，RunPodSandbox +0.31% | PASS |
| 每轮 start-vm 展开≤250ms | 286.197～401.680ms | FAIL |
| 5×10 CRI receive→start-vm P95≤650ms | 995.585ms | FAIL |
| restart/cancel/release 后 exact-zero | 全部为 0 | PASS |

终审决定把前四项和生命周期/exact-zero 作为 S5.5b 的退出条件；两个失败的端到端检查点改为
累积预算：S5.5c 关闭前要求 receive→start-vm 并发 P95≤450ms，S5.5d 关闭前要求≤300ms，
并最迟在 S5.5d 重验 absolute VMM start spread≤250ms；S5.5f 再执行最终端到端门禁。
这样不会降低最终 SLO，也不会为了让 S5.5b 形式通过而把 S5.5c/d 的 netlink 和 journal
改动混入 keyed-lock 提交。同一 reviewer 最终 `PASS`（P0/P1/P2=0），S5.5b 可以进入
`DONE`，主线进入 S5.5c。

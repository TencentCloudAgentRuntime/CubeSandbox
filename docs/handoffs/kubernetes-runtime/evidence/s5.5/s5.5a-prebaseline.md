# S5.5a 启动与资源预基线

## 结论

本文件只记录进入 S5.5a 前的方向性探针，用于确定正式 A/B 范围，不是 S5.5a 验收报告，
也不能据此确定最终 `RuntimeClass.overhead`。

W1 上创建 5 个 `runtimeClassName: cube` 的缓存 BusyBox Pod；每 Pod request 为 10m/16Mi，
limit 为 100m/64Mi。稳定 30 秒后的观测如下：

| 指标 | 结果 |
|---|---:|
| Host Pod cgroup `memory.current` | 104.55～104.69MiB/Pod |
| Host Pod cgroup `memory.peak` | 105.59～106.27MiB/Pod |
| 节点 `MemAvailable` 差值摊销 | 约 119.4MiB/Pod |
| `cube-vmm-worker` PSS | 约 102MiB/Pod |
| CubeShim PSS | 约 6.1MiB/Pod |
| Host cgroup anon / kernel | 约 101MiB / 3.6MiB/Pod |
| 空闲 CPU | 约 1.7m/Pod |
| 启动累计 CPU | 约 1.08 CPU-s/Pod |
| PID | 约 24/Pod |

创建、稳定采样、清理和最终 exact-zero 的云端执行编号分别为 `inv-38cbj00tbx`、
`inv-v8cbi3g6m4`、`inv-v8cbkt07vb` 和 `inv-b8cbmp0s9s`。当时
`RuntimeClass/cube` 声明 250m/768Mi；64Mi workload 的 Pod parent 上限为 832Mi，Cube leaf
上限为 1.25GiB。配置上限不是实际常驻量，不应把 768Mi 当成实测 overhead。

## 已知不可比项

- 探针只有 5 Pod，没有 1/5/20 Pod 三轮密度曲线，也没有误差区间。
- 没有在同一节点、同一制品比较 embedded cold 与 worker cold，不能量化 worker 拆分成本。
- 当前 Kubernetes 路径是普通 cold boot；日志只有 `start vm start` 和约 2.7～3.0 秒后的
  `vm ready`，没有 RuntimeTemplate restore。原 Cube PVM 模板报告的 27～34MB/Sandbox 只能
  作为方向参照。
- `MemAvailable` 会受 page cache 和节点后台负载影响；正式报告必须与 cgroup、PSS、PSI 和
  启动峰值联合解释。

## S5.5a 正式关闭条件

W2 绑定最终 Host/Guest artifact SHA 后，完成 50 串行、5×10 并发、worker/embedded cold A/B
以及 1/5/20 Pod 三轮资源采样；所有 Pod 必须通过 Sandbox ID 关联 kubelet/containerd/
CubeShim/Cubelet/worker/Guest 时间线，阶段覆盖至少 95%，并由独立 reviewer 确认原始数据和
exact-zero 后才能将 S5.5a 标记为 `DONE`。

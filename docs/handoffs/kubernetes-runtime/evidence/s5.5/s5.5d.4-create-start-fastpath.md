# S5.5d.4 CreateSandbox / StartSandbox 快路径

## 结论

本轮在不放宽 Pod、cgroup、网络持久化和失败回滚语义的前提下完成两项优化：

- `CreateSandbox`：把 systemd scope 的 `GetUnit` 预检查与
  `StartTransientUnit(mode=replace)` 合并为原子的 `StartTransientUnit(mode=fail)`，消除一次
  D-Bus 往返及检查/创建竞态；scope 就绪轮询改为前 100ms 每 2ms 快速检查，之后退避到
  10ms，上限仍为 2s。
- `StartSandbox`：复用 netlink 创建 TAP 时返回的 queue FD，在 PREPARED 记录落盘后缓存，并在
  VMM handoff 时复制该 FD；进程重启或 TAP 已存在时仍走原有的 netns reopen 路径。

受控单节点 150 Pod A/B 中，Shim `CreateSandbox` 的 mean/p95 从
`367.10/748.97ms` 降至 `211.21/376.82ms`，`StartSandbox` 从
`193.17/331.37ms` 降至 `174.15/240.81ms`。10 节点 1500 Pod 两轮均为
1500/1500 Ready、零 Warning、零重启；端到端 all Ready 从历史同配置的 11.00s 降至
8.60s/8.23s。

## 实现与约束

### Host cgroup

- systemd 使用 `mode=fail` 原子拒绝同名 unit，保留“不复用既有 scope”的 fail-closed 语义。
- 创建后仍同时校验 scope 路径、目标进程 cgroup、父目录 identity 和 leaf identity；只改变轮询
  间隔，不缩短 2s 最终 deadline。
- burst 测试发现 action helper 会继承另一个 sandbox 的 lifecycle 环境。入口现仅对已知短命
  action（`start`、`delete`、reaper、watchdog、probe）跳过 server gate；空 action 和未知 action
  继续执行 gate，以保留 containerd dispatcher 兼容性。

### TAP FD handoff

- 新建 TAP 时保留首个 queue FD，恢复为 blocking，并执行与原 reopen 路径一致的 vnet header 和
  offload ioctl。
- TAP ownership alias 在 FD 规范化之前写入；后续失败可由 durable rollback 回收。
- FD 仅在 PREPARED 状态成功落盘后进入缓存；错误、回滚、Release 均关闭 FD。
- 已存在 TAP、服务重启或缓存缺失时仍进入原 `Open` fallback，不依赖内存状态恢复正确性。

# S5.4a cube-vmm-worker 普通启动契约

## 范围

本契约只冻结普通启动所需的进程、IPC、FD、故障和性能边界。RuntimeTemplate、PodSnapshot、
Pause/Resume 的产品语义留到 S6.1；它们只能通过协议版本扩展，不得改变本轮已经验收的普通
启动命令含义。

## 进程与资源所有权

- CubeShim 是 containerd Sandbox/Task 的唯一适配器、普通启动编排者和 durable lifecycle
  owner。它调用 Cubelet、持有 lease/generation、操作 Guest Agent，并创建及回收 sandbox
  leaf/scope。
- Cubelet 只管理 RuntimeResource lease、Guest assets、shared root、TAP 与网络 attachment；
  不管理 VMM 进程。
- 每个 Pod 只有一个 `cube-vmm-worker`。worker 只管理 VMM、vCPU、Guest memory、virtiofs 和
  热插拔设备；不链接 Cubelet client、不持有 RuntimeResource 凭据，也不理解 CRI/Kubernetes。
- worker 必须先被 CubeShim 放入 sandbox leaf 并完成 PID/start-time/executable、cgroup 路径和
  leaf inode 回读，随后才允许创建 VMM 线程、vCPU 或 Guest memory。CubeShim 本身可作为轻量
  scope owner 留在 leaf；worker 必须是 leaf 内唯一 VMM/Guest-memory 进程。

## IPC v1

CubeShim 在 `fork/exec` worker 前创建两个 Unix `SOCK_SEQPACKET` socketpair：一个请求/响应
控制通道，一个单向事件通道。所有新 FD 默认 `CLOEXEC`；child `pre_exec` 只对两个 child
endpoint 清除 `FD_CLOEXEC`，并使用 async-signal-safe `close_range`/`close` 关闭除 stdio 和这
两个 endpoint 外的全部 FD。parent endpoint 始终保持 `CLOEXEC`，spawn 返回后父进程立即关闭
child ends；worker 入口重新给两个 IPC endpoint 设置 `CLOEXEC`。解除 gate 前 CubeShim 通过
`/proc/<pid>/fd` 回读该 allowlist，并同时验证 IPC 确已跨 exec 存活。TAP/设备 FD 不得继承，
只能在 placement 后以 `SCM_RIGHTS` 交付。接收使用
`MSG_CMSG_CLOEXEC`，数据或 control 截断、畸形/重复/out-of-range slot 均关闭本包全部 FD 并
poison worker。控制包具有 `magic`、`version`、单调 `request_id`、操作码和 payload，响应必须
回显 version 与 request_id。包大小、FD 数量、重复/乱序响应、未知版本或未知操作全部 fail closed。

普通启动 v1 操作面为：`Hello`、`Launch`、`Ping`、`CreateVm`、`BootVm`、`JoinVmm`、`SetFs`、`AddDevice`、
`RemoveDevice`、`DeleteVm` 和 `ShutdownWorker`；事件面至少包含 `VsockServerReady`、
`VmShutdown` 和协议错误。现有 snapshot/pause/resume 方法在 worker 后端先以同一通道保持行为
等价，但不视为 S6 产品契约。

控制通道同一时刻只允许一个 in-flight request；CubeShim mutex 与 worker 的严格递增
`request_id` 双重执行该规则。`Hello` 只能执行一次且不创建 VMM；`Ping` 可重试，其他 mutation
均为 at-most-once，发生发送后超时、响应丢失、乱序、未知响应或任一通道异常时不得猜测重试，
而是 poison worker 并走精确清理。普通命令 deadline 为 10 秒，Hello/placement 为 2 秒；
后续长时 snapshot 命令在 S6 使用独立 deadline。`VM_INTENT` 指 durable RuntimeResource owner
的 `vm_state=INTENT`，`VM_ALLOCATED` 指 Guest Sandbox 创建成功后的同字段提交，不另造隐式
commit 状态。

`CreateVm` 中的 TAP 不传裸 Host FD 数字：请求 payload 只保存 descriptor slot，真实 descriptor
与同一个 seqpacket 通过 `SCM_RIGHTS` 原子交付；worker 校验 slot 数量与 rights 数量完全一致后
重写 VM config。接收端在 VMM 完成 `dup` 后关闭 handoff descriptor。未来 VFIO/块设备复用
相同的显式 slot 表，不增加 worker 到 Cubelet 的反向连接。

## 启动线性化点

1. CubeShim 完成 RuntimeResource Prepare/TAP acquire，并持久化 TAP/VM INTENT。
2. fork 前持久化 `WORKER_SPAWN_INTENT`：generation、operation epoch、随机 launch nonce、预期
   executable identity 和协议版本。exec 后 worker 设置 parent-death signal，并校验 parent PID；
   收到控制 EOF、parent death 或 2 秒内未完成 Hello 时，在创建任何 VMM 资源前退出。
3. CubeShim exec worker，发送仅校验协议/nonce/peer pid 的 `Hello`；worker 仍停在 receive gate。
4. CubeShim 把 worker 放入已验证的 sandbox leaf，持久化 PID/start-time/executable/cgroup/
   nonce 为 `WORKER_ALLOCATED` 并再次回读。Shim 在身份提交前退出时，watchdog 只按 spawn intent
   的 executable+nonce+generation 扫描并通过 pidfd 精确回收；匹配不唯一时 fail closed 并报警。
5. CubeShim 发送 `Launch`；收到成功响应前 worker 不接受 `CreateVm`。
6. CubeShim 以 `SCM_RIGHTS` 发送 VM config/TAP，执行 `BootVm`，等待
   `VsockServerReady`，再连接 Guest Agent并执行 `CreateSandbox`。
7. Guest Sandbox 成功且 lifecycle `VM_ALLOCATED` durable 后，CRI StartSandbox 才返回成功。

## 故障与恢复

| 故障点 | 对外结果 | 收敛动作 |
|---|---|---|
| fork 前 INTENT 后 Shim 退出 | StartSandbox 失败 | child 由 PDEATHSIG/Hello timeout 自退；watchdog 以 nonce+executable+generation 复核，清理 INTENT |
| worker exec/Hello/placement 失败 | StartSandbox 失败 | pidfd 精确终止 child，关闭 FD，回滚 TAP/VM INTENT，Release lease |
| worker 在 VM commit 前退出 | StartSandbox 失败 | CubeShim 等待 child，清理 leaf/RuntimeResource，必须 exact-zero |
| worker 在 Ready 后退出 | Sandbox 进入 Failed/Exited | 通知容器退出，幂等 Stop/Delete，释放 lease |
| CubeShim 退出、worker 仍存活 | S5.4b 明确不重连 | 控制 EOF/PDEATHSIG 触发 worker 自退，watchdog 按 durable PID/start-time/executable/cgroup/nonce/epoch 精确回收并释放，kubelet 重建 Pod |
| Cubelet 重启 | 已运行 VM 不受影响 | CubeShim 以 lease/generation Inspect/Release 重试，不让 worker调用 Cubelet |
| containerd 重启 | Pod 保持运行 | 现有 Shim/worker 不退出，containerd 重连 Shim socket |

`CUBE_VMM_BACKEND=embedded` 是 PoC 回滚开关；最终 E2E 和性能证据必须显式记录
`worker`，不得把 embedded 样本混入统计。worker 二进制默认从 CubeShim 同目录解析，也允许
测试时用 `CUBE_VMM_WORKER_PATH` 指定。

## 性能口径与门禁

最终目标（S5.4d）保持：预拉取、单容器、无 probe Pod 的 `PodScheduled→Ready P95≤1s`，
`RunPodSandbox receive→Ready P95≤700ms`；50 次串行与 10 并发成功率 100%，另报 P50/P99，
并用日志证明没有 PullImage。普通 boot 和未来 template 命中/miss 分开统计。

在进入耗时较长的 Node E2E 前，S5.4c 的普通 boot 门禁为：相同负载
`RunPodSandbox receive→Ready P95≤2s`、create→Ready P95≤2.5s，正常路径
`systemctl show=0`，worker placement 强校验最多一次，50 次串行与 10 并发无失败。若普通 boot
仍不能达到最终一秒目标，不阻塞 worker 路径 Node E2E；差距必须按时间段量化，并在 S6.2 用
RuntimeTemplate 关闭后补跑受影响 E2E。

固定负载为 `runtimeClassName: cube`、`imagePullPolicy: Never`、预拉取并记录 digest 的
`busybox:1.36.1`，单容器执行 `sleep 3600`，无 init/sidecar/probe/volume，request/limit 固定为
`100m/64Mi` 与 `1CPU/128Mi`，网络使用同一 Cilium 配置。串行 50 次；并发为 5 轮、每轮同时
10 个 Pod，共 50 个样本。任一失败都使门禁失败，不从延迟分布删除；失败耗时另列。

Pod 主口径由同一测试进程使用 `CLOCK_MONOTONIC`：第一次 watch 到 `PodScheduled=True` 为起点，
第一次 watch 到 `Ready=True` 为终点；同时保存 API `lastTransitionTime` 供核对。runtime 口径是
kubelet 发起 CRI `RunPodSandbox` 到其成功返回；Shim 子分段是 Sandbox `CreateSandbox` receive
到 `StartSandbox` reply。所有 Host 进程内时间戳使用同一节点 `CLOCK_MONOTONIC`，Guest 只报告
相对阶段，不与 Host 直接相减。P95/P99 使用 nearest-rank：排序后第
`ceil(0.95*N)`/`ceil(0.99*N)` 个样本。

统一记录分段时间戳：client create accepted、PodScheduled observed、CRI RunPodSandbox
begin/end、CubeShim CreateSandbox receive、Cubelet prepared、worker spawn intent/spawned/Hello、
worker placed/allocated、VMM launched、VM created、VM booted、vsock ready、Agent sandbox ready、
StartSandbox reply、Pod Ready observed。

## S5.4b 验收

- release build 同时产出并安装 CubeShim、`cube-vmm-worker` 与 `cube-runtime`；协议单测覆盖版本、
  request_id、截断包、FD 数量/slot 不符、IPC 跨 exec、gate 前 FD allowlist、parent death/Hello
  timeout 和 worker 提前退出。
- worker feature flag 下普通 Create/Start/Stop/Delete、多容器、取消创建、containerd restart 结果与
  embedded 基线等价；worker 位于目标 leaf，VMM 线程/Guest memory 不再属于 Shim 进程。
- worker kill、Shim kill 和 Cubelet restart 均得到上述确定结果；每轮清理后 Sandbox/VM/TAP/
  mount/active lease exact-zero。
- embedded 回滚路径可启动和删除 Pod；任何回滚不得沿用 worker 的残留状态。

估算：每个用例都由 `aggregate-nodeconformance.py` 使用源文件、行号、叶节点文本和容器层级
组成的唯一键归入且只归入一个能力域。

## 17 个 Failed 用例及原因

### A. memory-backed EmptyDir 应呈现 tmpfs：12 项

| 位置 | 用例 |
|---|---|
| `empty_dir.go:58` | root 容器新文件应具有 FSGroup ownership |
| `empty_dir.go:62` | non-root 容器新文件应具有 FSGroup ownership |
| `empty_dir.go:66` | 不存在的 volume subPath 应具有正确 mode/owner/FSGroup |
| `empty_dir.go:70` | FSGroup 文件应支持 root、0644、tmpfs |
| `empty_dir.go:78` | tmpfs volume 应具有正确 FSGroup mode |
| `empty_dir.go:89` | tmpfs volume 应具有正确 mode |
| `empty_dir.go:99` | root、0644、tmpfs |
| `empty_dir.go:109` | root、0666、tmpfs |
| `empty_dir.go:119` | root、0777、tmpfs |
| `empty_dir.go:129` | non-root、0644、tmpfs |
| `empty_dir.go:139` | non-root、0666、tmpfs |
| `empty_dir.go:149` | non-root、0777、tmpfs |

直接错误均为：期望 `mount type ...: tmpfs`，实际为十进制 `1702057286`，即
`0x65735546`（FUSE）。文件内容、UID/GID、FSGroup 和 mode 的实际输出均正确。

根因是 kubelet 在 Host 创建 tmpfs，Cube 再通过 virtiofs 将它导入 Guest；Guest/容器看到的
文件系统身份是 FUSE，而不是原 Host tmpfs。修复不能伪造 `statfs`，需要在 Guest 内创建 Pod
级 tmpfs，并重建跨容器、subPath、accounting、删除和快照语义。责任为 Cube 架构差异，跟踪
`K8S-OQ-025`，目标 S6.1。

### B. MirrorPod 暂时卸载失败后重建：1 项

- 位置：`mirror_pod_test.go:207`。
- 用例：static/mirror Pod 因卷暂时无法卸载后仍应成功重新启动。
- 直接错误：120 秒超时。
- 定向复核证明 privileged 门禁已生效、Guest 内 NFS server Pod 已 Ready；随后 Host kubelet
  挂载 `PodIP:/` 时，NFS server 返回 `No such file or directory`。
- 根因：Guest 内的 NFS server 无法稳定 re-export virtiofs-backed EmptyDir。需要 Guest-local
  可 export 文件系统、块设备或专用卷后端，并定义快照与清理语义。跟踪 `K8S-OQ-035`，S6.1。

### C. 不支持 RRO 时的普通只读嵌套 mount：1 项

- 位置：`mount_rro_linux_test.go:130`。
- 用例：runtime 不支持 recursive read-only 时，仍应接受普通 non-recursive read-only mount。
- 直接错误：约 6 秒后停止等待；定向报告中 mount init 成功，测试容器实际启动后 exit 1。
- 根因：Cube 正确广告 `recursive_read_only=false`，但 Host 嵌套 mount 经 virtiofs 导入 Guest
  后丢失 mount identity。需要在 Guest 重建 mount topology 或使用不同的卷通道。跟踪
  `K8S-OQ-034`，S6.1。

### D. CPU Manager sidecar 复用独占 CPU：1 项

- 位置：`cpu_manager_test.go:1909`。
- 用例：业务/app 容器应复用已经结束的普通 init 独占 CPU，但不得复用仍在运行的 sidecar
  独占 CPU，并验证三者的 CPU 集合关系。
- 直接错误：上游测试读取 Host
  `cri-containerd-<container>.scope/cpuset.cpus.effective`，文件不存在。
- 根因：Cube 在 Host 只有 Pod VM cgroup；per-container cgroup 与 cpuset 位于 Guest。Host→Guest
  CPU ID 映射和其他 PodResources/CPU Manager 用例已经通过，本项失败于测试的 Host
  per-container cgroup 假设。需要版本化 Guest stats/topology 汇总或 runtime-aware 测试接口，
  不创建伪 Host cgroup。跟踪 `K8S-OQ-036`，S6.1。

### E. Summary API I/O PSI：1 项

- 位置：`summary_test.go:461`。
- 用例：I/O 压力期间 `/stats/summary` 应报告 I/O PSI。
- 直接错误：等待 120 秒后仍观察到目标容器 `io.psi.some.avg10=0`，期望大于 `0.1`。
- 根因：I/O stress 与 pressure signal 发生在 Guest per-container cgroup，kubelet 当前读取 Host
  cgroup/CRI 汇总，未获得该 Guest 信号。需要 Agent→worker→Shim/CRI 的 per-container PSI
  聚合协议。跟踪 `K8S-OQ-036`，S6.1。

### F. kubelet client CA 热重载：1 项

- 位置：`kubelet_server_tls_test.go:168`。
- 用例：从磁盘重新加载 kubelet client CA。
- 直接错误：访问 kubelet `/configz` 最终 `context deadline exceeded`。
- 根因：本次 runner 挂接现有 kubeadm apiserver，并使用临时 `kubelet-e2e.service`。测试替换
  kubelet client CA 后，现有 apiserver 没有同步建立新的信任；该调用不经过 Cube Sandbox。
  应使用 e2e_node 自管 control-plane 或专用 apiserver fixture 重跑。责任为测试环境限制，
  跟踪 `K8S-OQ-037`。

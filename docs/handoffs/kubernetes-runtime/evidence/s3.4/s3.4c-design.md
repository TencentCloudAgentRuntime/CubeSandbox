# S3.4c Host Pod VM 资源包络设计

状态：`APPROVED`。同一 reviewer 已完成四轮复审并明确返回
`APPROVE S3.4c DESIGN`；S3.4c.2 实现必须遵守本文冻结契约。

## 1. 结论

Cube 不重算 Kubernetes 的 init container、restartable sidecar、业务容器与 Pod-level
resources 聚合，也不接管 kubelet 创建的 Pod cgroup。Host 包络采用两层、单一所有权：

1. kubelet 独占 Pod 父 cgroup，写入 Kubernetes 有效 resources 加 RuntimeClass overhead；
2. CubeShim 独占父 cgroup 下、由 containerd OCI sandbox `linux.cgroupsPath` 指定的叶子
   scope；
3. 叶子承载 CubeShim server 及其 VMM、vCPU、virtiofs 和异步辅助线程/子进程，并设置静态
   VM 容量 ceiling；
4. Guest Agent 独占 VM 内 per-container cgroup。

实现只修改 CubeShim、节点配置和 RuntimeClass 清单，不修改 containerd，不在 Guest 中运行
containerd。动态 resize 时 kubelet 更新父层，现有 Task Update 更新 Guest 目标容器，静态
leaf 不重算；Cube 不重复写父层，也不伪造跨 owner 原子事务。

### 2.2 containerd、bootstrap 与进程模型

containerd 2.3.4 在 Shim start action 前已生成 bundle `config.json`。systemd driver 的 OCI
路径为 `<pod.slice>:cri-containerd:<sandbox-id>`，cgroupfs driver 为
`<parent>/<sandbox-id>`。containerd 还写入 `io.kubernetes.cri.container-type=sandbox` 与
`io.kubernetes.cri.sandbox-id=<sandbox-id>`，这两个 annotation 才能区分 managed Sandbox
与共用 start path 的 legacy Task；`cgroupsPath` 本身不是分类器。
[containerd cgroup path](https://github.com/containerd/containerd/blob/v2.3.4/internal/cri/server/podsandbox/helpers_linux.go)、
[containerd CRI annotations](https://github.com/containerd/containerd/blob/v2.3.4/internal/cri/annotations/annotations.go#L25-L40)

当前 start action 先 spawn server，之后才可能收到 `CreateSandbox` 或 `CreateTask`；bootstrap
protobuf 的 extension tag 8 当前被忽略。VMM、vCPU、virtiofs 都是 server 内线程。Linux
cgroup v2 写 `cgroup.procs` 会迁移整个线程组，之后的新线程/子进程继承该 cgroup。
[Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

spawn 后现有 `set_cgroup_and_oom_score` 只从已经消费完的 stdin 读取可选
`Options.shim_cgroup`，所以当前实际只调 OOM score，不会再次移动 server；新实现仍必须做
spawn 后 membership readback。
[rust-extensions shim-v0.11.0](https://github.com/containerd/rust-extensions/blob/shim-v0.11.0/crates/shim/src/cgroup.rs#L46-L67)

containerd 2.3.4 local sandbox controller 的 `Update` 是 no-op，shim Sandbox service 也没有
Update RPC。它不影响 Host enforcement，因为 kubelet 已更新父层；但它意味着 Cube 首版
不能依赖 sandbox update 获得新的 aggregate。
[containerd sandbox Update](https://github.com/containerd/containerd/blob/v2.3.4/plugins/sandbox/controller.go#L339-L345)

`CreateSandbox`。因此 stdout flush 不是接管提交点；server 收到第一个身份匹配的

[containerd binary Start](https://github.com/containerd/containerd/blob/v2.3.4/core/runtime/v2/binary.go#L120-L153)、

## 3. 所有权、配置与预算

| 对象 | 唯一 owner | Cube 权限 | 规则 |
|---|---|---|---|
| Pod 父 cgroup | kubelet | 只读 | 不创建、不写 controller、不删除 |
| sandbox OCI leaf/scope | CubeShim | 创建、写自身 ceiling、回收 | 路径只来自已验证 OCI spec |
| Shim/VMM/vCPU/virtiofs | CubeShim | 只位于 leaf | 任一 thread/process 逃逸均失败 |
| Cubelet、CNI、containerd | 节点服务 | 不迁移 | 不计入单 Pod leaf |
| Guest per-container cgroup | Guest Agent | S3.4b 范围 | 不写 Host |

有效上限按速率/层级取祖先与叶子的交集，而不是直接比较不同 period 的 quota 数字：

```text
effective_host_limit = min(kubelet_pod_parent, cube_static_vm_leaf)
```

### 3.1 节点 overhead 配置

节点配置路径由 `CUBE_RUNTIMECLASS_OVERHEAD_CONFIG` 指定，未设置时固定为
`/etc/cubesandbox/runtimeclass-overhead.json`。managed Sandbox 要求该文件存在且 schema
合法；不提供隐式运行时 fallback。PoC 安装清单生成：

```json
{
  "schema_version": 1,
  "minimum_cpu_millicores": 250,
  "minimum_memory_bytes": 268435456,
  "host_pids_max": 512
}
```

RuntimeClass 默认声明 CPU `250m`、memory `256Mi`。CRI overhead 的 CPU rate 与 memory 必须
分别不小于节点 minimum；高于 minimum 的 RuntimeClass 被接受并使用其实际值，只有缺失、
部分缺失或任一维低于 minimum 才 fail-closed。S3.4c.4 可以依据压力证据提高安装默认值，
不能在没有证据时降低。配置文件、RuntimeClass 和 effective 值都进入证据。

overhead 只接受本阶段可解释的 CPU/memory 与 `unified["memory.oom.group"]="1"`；非零
OOMScoreAdj、cpuset、swap、hugepage 或其他 unified key 明确拒绝。CPU shares 参与幂等
fingerprint，但不是 ceiling 算法输入。

### 3.2 leaf 预算与 checked normalization

创建 VM 前把 overhead CPU rate 统一到 100000us period：

```text
normalized_overhead_quota = ceil(overhead.quota * 100000 / overhead.period)
leaf.cpu.max              = (vcpu_count * 100000 + normalized_overhead_quota) 100000
leaf.memory.max           = guest_memory_bytes + overhead.memory_limit_in_bytes
leaf.pids.max             = node.host_pids_max
leaf.memory.oom.group     = 1
```

- `period<=0`、`quota<=0`、`memory<=0`、vCPU/memory 为零均拒绝；
- 乘法、ceil 加法和最终加法用 checked `u128`，结果必须可表示为 controller 接受的正整数；
  任一 overflow 拒绝，不截断、不饱和；
- 比较 overhead minimum 或 parent/leaf CPU 上限时用 checked 交叉乘法比较 rate；
- leaf 不从 container requests/limits 重算，不设置 `cpu.weight`/`memory.low`；父层是 QoS
  仲裁点；
- `pids.max` 只限制 Host threads/processes，不代表 Guest workload PID 数。Guest PIDs 继续由
  S3.4b per-container controller 执行，PoC kubelet 保持 `podPidsLimit=-1`。

## 4. bootstrap 分类、路径与身份

### 4.1 精确分类器

start action 读取同一 bundle 的 OCI annotations 后只产生三类结果：

1. `container-type=sandbox`：只在 bootstrap namespace=`k8s.io`、`sandbox-id` 等于
   `instance_id`、OCI cgroupsPath 合法时判定 `ManagedSandbox`；任一缺失/不等立即失败；
2. `container-type=container`：要求 namespace=`k8s.io`，同时必须有非空且通过共享
   containerd-ID 语法校验的 `sandbox-id`；它不要求等于当前 container `instance_id`，判定
   `LegacyTask`，不创建 Host Pod leaf；
3. 两个分类 key 都不存在：判定 direct/low-level `LegacyTask`；只有一个 key、空/非法
   sandbox-id、未知 type 或冲突组合都拒绝。

server 端在任何 `CreateSandbox` 副作用前再次加载 bundle，只有 `ManagedSandbox` 才接受；
`LegacyTask` 收到 `CreateSandbox` 必须失败。这样 legacy `CreateTask` 保持原路径，同时损坏的
sandbox annotation 不能绕过 Host 包络。

### 4.2 路径等价校验

- systemd path 必须恰好为 `<pod-slice>:cri-containerd:<instance-id>`；展开 slice 后，leaf
  parent 必须等于 CRI `cgroup_parent` 的规范化 cgroup-v2 目录；
- cgroupfs path 的 basename 必须等于 instance ID，parent 必须等于规范化
  `cgroup_parent`；
- 目标必须在唯一 cgroup-v2 mount 下且非 root，拒绝 symlink、`..`、错误 manager、错误
  prefix、跨 mount 和身份不一致；
- Cube 不自行生成替代路径，也不写/delete parent。

### 4.3 bundle 外的 canonical lifecycle record

节点安装一个长期运行的 `cubesandbox-shim-watchdog.service`。它由 systemd 启动、
`Restart=always`，进程必须经 readback 位于独立
`/system.slice/cubesandbox-shim-watchdog.service`，同时扫描 HostCgroup 与
RuntimeResource cleanup queues。新 Shim 在任何 cgroup/socket mutation 前必须确认该 service
active、PID identity/cgroup 正确，并在
`/data/cubelet/shim-lifecycle/<identity-hash>/` 建立 durable lifecycle、HostCgroup owner、
RuntimeResource owner 与 lock files；服务或持久目录不可用时零 mutation 失败。不存在从 Pod
leaf `setsid` 启动的临时 reaper。

外部 record 是权威，bundle 的 `cube-host-cgroup.json` 与 `cube-shim-server.json` 只是可重建
mirror。record 包含 schema、phase、classification、namespace/instance、bundle path/dev/inode、
OCI/Host path、manager、helper identity、server identity，以及全局 socket 的 path/dev/inode。
它还包含独立的 `create_state=NONE|IN_PROGRESS|SUCCEEDED|FAILED`、canonical request
fingerprint 与最后结果；lifecycle phase 表示 containerd/cleanup ownership，create_state 表示
Sandbox 创建结果，两者不能混用。
同目录的 `host-cgroup-owner.json` 从 PREPARED 起包含 manager/path/parent/identity/WAL 引用；
`runtime-resource-owner.json` 从 PREPARED 起即以 `EMPTY` 存在，此后每项 lease、TAP、mount、
VM 等资源都必须 INTENT-before-allocate，并在分配后补齐 generation/handle/readback。INTENT
必须包含确定性 idempotency/allocation key 与 provider lookup/release 参数，使 scanner 在“分配已
发生但 handle 尚未回写”时能查到并释放或证明未创建；不能提供该 reconcile 契约的资源类型在
preflight 就拒绝。它们是 bundle 消失后仍可重放的 canonical cleanup source，不允许只把资源
身份留在 bundle。
PREPARED 还在 spawn 前保存一次性 256-bit launch nonce 的 SHA-256、预期 executable
path/dev/inode、完整 argv、目标 cgroup、socket parent dev/inode，并断言目标 socket 当时不存在。
phase 单调为：

```text
PREPARED -> SERVER_IDENTIFIED -> SOCKET_READY -> CONTAINERD_COMMITTED
任一上述运行 phase -> CLEANUP_REQUIRED -> CLEANUP_OWNERS_DURABLE
                     -> SERVER_STOPPED -> DONE
```

每个 identity 目录有不位于 bundle 的固定 `record.lock` 与 `operation.lock`。所有 record RMW
持有前者，校验 generation、当前 phase、完整 identity、operation-owner epoch 与严格递增
sequence；过期 writer 的 compare-and-swap 失败，必须重新读取。controller write/readback 与
RuntimeResource allocate/release 还必须持有 `operation.lock`，并在每次副作用前短暂取得
`record.lock` 校验 epoch 未被 revoke、持久化 INTENT，随后释放 `record.lock` 才执行副作用；
scanner 的 revoke 只持有 `record.lock`，释放后才等待/取得 `operation.lock`，禁止反向持锁。
PREPARED 同时建立 `operation_owner={kind:helper, immutable_identity, epoch=E0}`；server 自注册不
自动获得写权。首个 takeover RPC 把 owner 以 CAS 转给 server 并递增 epoch，之后每次 scanner
revoke/handoff 也必须递增 epoch；epoch 永不复用。
每次 transition 都以同目录临时文件、file fsync、rename、parent fsync 完成。PREPARED 与两个
owner source 在首次 mutation 前存在；server identity 在 readiness 前持久化；socket bind 后
补齐 inode。stdout flush 后 record 仍由 watchdog 持有，绝不视为 committed。

server 收到并完成结构/instance/bundle 分类校验的首个 `CreateSandbox`（legacy 为
`CreateTask`）时，在任何 RPC 副作用前把 external record 原子推进为
`CONTAINERD_COMMITTED/create_state=IN_PROGRESS` 并保存 canonical fingerprint，watchdog
durable ack 后才继续。这一 RPC 证明 containerd 已完成 response parse、socket connect、
`bootstrap.json` 和 manager add。首个 Create 成功时先 durable 标记 `SUCCEEDED` 再返回；其
semantic validation、controller 或 runtime allocation 失败时先 durable 标记 `FAILED`，但在
failure result drain 前仍保持 `CONTAINERD_COMMITTED`。同一 server 对 Create 做 per-sandbox
single-flight：并发同 fingerprint 请求等待并复用首个最终结果，不同 fingerprint 立即返回
`ALREADY_EXISTS`。已 `SUCCEEDED` 的
重复同 fingerprint Create 只做幂等 readback；不同 fingerprint 不改变 phase、不清理现存
sandbox。containerd crash 后已 committed、`IN_PROGRESS` 或 `SUCCEEDED` 且 server 存活的记录
保留以允许恢复/重连；server 死亡、显式 delete、首个 Create 失败或已定义为 terminal 的 runtime
failure 才由 scanner 推进 `CLEANUP_REQUIRED` 并收敛。

`FAILED` record 必须先持久化完整 ttrpc code/message、fingerprint、waiter count 与
`result_published_at`。server 把同一结果发布给当时全部 single-flight waiters，全部 handler
离开 single-flight 后再持久化 `failure_drained=true`；之后 server 才请求
revoke/`CLEANUP_REQUIRED`。若未 drain，只有 server 原
身份已死或 durable result 发布后 30 秒超时，scanner 才可 revoke并 handoff；无论哪条路径，都
必须到 `CLEANUP_OWNERS_DURABLE` 后才可终止 live server。不同 fingerprint 的
`ALREADY_EXISTS` 不进入该计时器。超时路径仍保留 FAILED result，后续审计能区分业务错误与
transport interruption。

PREPARED/SERVER_IDENTIFIED/SOCKET_READY 在 helper 原身份死亡且 30 秒内没有 commit 时，由
watchdog 先 revoke epoch并把两个 owner source handoff 到 durable queues，再精确终止 server、
删除匹配 socket、回收 Host leaf；因此 response 之后的 parse、connect、`shim-binary-path`、
`bootstrap.json`、manager-add 任一失败都仍有 bundle 外 owner。scanner 自身退出由 systemd
restart 后重新扫描 durable queue，不依赖一次性子进程。

### 4.4 process identity fencing

进程 identity 明确拆成两组，不能再把 containment 漂移当成 PID 身份漂移：

- immutable identity：recorded PID 对应 pidfd、boot ID、starttime、exe dev/inode、完整 argv、
  bundle dev/inode、namespace/instance、launch nonce/generation；
- containment identity：预期 cgroup path/dev/inode 与当前 `/proc/<pid>/cgroup`。

每次 signal 前必须先 `pidfd_open`，确认 pidfd 仍存活，再校验全部 immutable identity，并在 signal
前重复一次。immutable 任一 mismatch 永不 signal，PID 不存在视为原进程已死。正常 cleanup 要求
containment 也匹配；唯一例外是 scanner 已观察到 immutable 全匹配但 containment 不匹配，并在
record durable 标记 `CONTAINMENT_BREACH`、保存 observed cgroup identity、revoke owner epoch 且
两个 cleanup queue 均进入 `CLEANUP_OWNERS_DURABLE`。此时 cgroup mismatch 本身是被处置的
违规，scanner 仍只向原 pidfd signal；同 sibling cgroup 中 argv/exe 相同但 PID/starttime/nonce
不匹配的诱饵永不 signal。升级前遗留且没有新 identity record 的 Shim 只允许 graceful
Shutdown/等待，不再按裸 PID 强杀。

为关闭“spawn 成功但 helper 在写 ServerIdentity 前被 SIGKILL”的窗口，server 在 Rust main
的第一段逻辑用继承的 launch nonce 向 external record 自注册，然后才等待 readiness gate；
parent 也在 `Command::spawn` 返回后注册同一 PID。scanner 允许从唯一 leaf 中收养尚未登记的
child，但必须同时匹配 nonce hash、exe dev/inode、完整 argv、bundle、namespace/instance、
目标 cgroup，以及 PPID=helper 或 helper 已死后的 PPID=1，之后才固化 starttime/boot ID 并
使用 pidfd。不能满足全部条件的 PID 永不 signal。

socket 已登记 inode 时只按 path/dev/inode unlink。若 server 在 bind 与 SOCKET_READY transition
之间死亡，scanner 只有在 PREPARED 已证明 path 原先不存在、parent identity 未变、对象仍是
Unix socket、没有更新 generation/record 声明同一路径、没有 live FD owner，且时间晚于
PREPARED 时才清理；否则保留并报告 identity mismatch。

## 5. 启动、失败回滚与删除

### 5.1 readiness gate 与 start guard

managed start action 的完整顺序是：

```text
读取 bootstrap + OCI，分类并校验 path
  -> 验证长期 watchdog service/cgroup并持久化 external PREPARED
  -> systemd transient scope / cgroupfs leaf 创建并加入 helper，readback
  -> 创建私有 pipe gate，spawn server；server 在 main 入口阻塞
  -> child 先用 launch nonce 自注册再等 gate；parent 同时 pidfd/身份注册并调整 OOM score
  -> 验证 systemd job/state/cgroup/member 后 release gate
  -> server 校验 identity + membership + unit state 后才 bind/readiness
  -> socket identity durable transition；helper 等 readiness，原子写 address
  -> helper 迁回原 cgroup并 readback（server 留在 leaf）
  -> 写完整 BootstrapResult 成功
  -> helper 退出；external record 仍未 commit并由 watchdog 持有
  -> 首个身份匹配 CreateSandbox/CreateTask RPC durable COMMIT
```

legacy 也使用 gate 和 ServerIdentity，但不创建/迁入 Host leaf。把 helper 放入 leaf 后 guard
一直保持 armed，直到 BootstrapResult 完整 flush 成功；随后只是本地 guard 结束，外部 watchdog
ownership 不结束。spawn、pidfd、OOM adjustment、identity
持久化、gate、readiness I/O、child early-exit、address 写入、helper 迁回或 response 写入中的
任一错误都走同一 guard。

guard 顺序为：revoke epoch并推进 `CLEANUP_REQUIRED` → 两个 external owner source handoff 且
readback `CLEANUP_OWNERS_DURABLE` → 精确终止并等待 server（若已 spawn）→ helper 迁回原
cgroup并 readback → 让两个长期 queue 确认 leaf/resource cleanup → 删除完全匹配的 bundle
mirror。任一 handoff 未 durable 时不得 signal server。helper 即使在任意指令被 SIGKILL，
预先存在的 external record/owner source 仍会被长期 scanner 发现；scanner 等 helper 原身份退出，
只对满足 4.4 谓词的 server 使用 pidfd，并按 path/dev/inode 删除全局 socket。所有 response 后
failpoint 与 containerd crash 都由 PREPARED→COMMITTED 协议覆盖。

### 5.2 systemd/cgroupfs 安全回收

不调用 `cgroups-rs 0.5.1` 的 `SystemdManager::destroy` 或 `FsManager::destroy`：前者
`StopUnit` 会 signal unit 成员，后者会先把残留进程迁到 root。

- systemd scope 由专用 wrapper 以 `PIDs=[helper]`、`Delegate=true`、
  `CollectMode=inactive-or-failed` 创建。gate release 前必须等待 StartTransientUnit job=`done`，
  连续五次（间隔 20ms）验证 `ActiveState=active`、`SubState=running`、`ControlGroup` 等于
  record 且 helper 是成员；server 过 gate 后立即重复 unit/state/membership 校验。任一采样
  inactive/dead 都 fail-stop并由 external scanner 清理，不能因 cgroup 内仍有 PID 而继续；
  committed server 存活期间 scanner 继续周期校验 unit state、ControlGroup 与 server
  membership；若出现成员仍存活但 unit inactive/dead 或 containment 漂移，先 revoke
  operation-owner epoch，把两个 canonical owner source 分别 handoff 到 durable queue，并推进到
  `CLEANUP_OWNERS_DURABLE`，之后才按 4.4 的 containment-breach 谓词精确终止原 server 并
  回收，不能继续承载 Pod；
  最后一个 member 退出后由 systemd 自动停止/collect，scanner 只观察收敛，空且 failed 时可
  `ResetFailedUnit`，永不调用 StopUnit/KillUnit；
- cgroupfs leaf 只有在规范化 identity 匹配、`cgroup.events populated=0`、`cgroup.procs` 和
  子 cgroup 为空时才直接 `rmdir`。若检查后有进程竞态加入，内核 `rmdir` 失败并进入 durable
  retry；绝不迁移或 signal 未记录进程；
- parent 永不参与回收。identity mismatch 或 non-target PID 只报告/重试，不猜测删除。

目标 `255.4-1ubuntu8` 不声明包含 #36801；每个新 package/build/boot 都必须先运行与实际属性
完全相同的 200 次竞态探针，保存 job/state/cgroup/member 和 exact cleanup。这个环境门禁加
每次启动的 gate 前后检查共同构成 PoC 兼容条件；探针失败则该节点不注册 Cube RuntimeClass。

### 5.3 CreateSandbox 与 controller transaction

server 在 `CreateSandbox` 先校验 bootstrap classification、CRI parent、overhead、node config
和重复 Create fingerprint，再选择 VM 规格。`cgroup_parent` 与完整 canonical overhead（包括
presence、全部 scalar、排序后的 unified/hugepage）必须进入 semantic fingerprint；同一
sandbox 的重复 Create 只有完全一致才幂等。

leaf controller 不是“原子写”，而是 crash-consistent WAL。structural decode 与 canonical
fingerprint 先完成；若 lifecycle 已有 Create，fingerprint 不同立即返回 `ALREADY_EXISTS`，早于
对新 parent/overhead 的 live semantic validation，完全相同才进入幂等 readback。首次 Create
再做完整 semantic/path/node-policy validation，失败返回 `INVALID_ARGUMENT` 或
`FAILED_PRECONDITION`，且零 controller 写入。

首个 Create 把 `operation_owner` 从 helper CAS 转为
`{kind:server, immutable_identity, epoch=E0+1}` 并与 fingerprint 一起 durable 写入；只有该
identity、该 epoch、`CONTAINERD_COMMITTED/IN_PROGRESS` 的 live server
能做 forward recovery。scanner 永不继续 VM 创建，只能在 server 已死、containment breach、
Create FAILED 或 cleanup 请求时以 `epoch=E+1, kind=scanner, revoked=E` 接管 cleanup。server 在
每项 controller/RuntimeResource 副作用前都按 4.3 的锁协议重新验证 E；revoke 后的 stale server
即使仍存活也不能继续写 controller 或分配资源。

WAL 流程：

1. 读取旧 `memory.oom.group`、`pids.max`、`memory.max`、`cpu.max`，完成
   `pids.current<=target`、`memory.current<=target` 和 controller/type preflight；
2. 在任何 controller write 前持久化整体 `PREPARED`，包含 transaction ID、owner identity/epoch、
   fingerprint、完整 old/target、固定 step 顺序与每步 `NOT_STARTED`；
3. 对 `memory.oom.group -> pids.max -> memory.max -> cpu.max` 的每一步，先把 step=`INTENT`
   durable fsync，再 write，再 exact readback，最后把 step=`APPLIED` 与 observed durable fsync；
4. 任一点 crash 后，当前唯一 owner 读取实际 controller：值等于 target 视为该 INTENT 已写，
   等于 old 视为未写，其他值进入 `DEGRADED` 且不猜测；forward/rollback 方向只由下表决定；
5. 全部 target readback 后先持久化整体 `CONTROLLERS_COMMITTED` 并 fsync，只有此状态才允许
   RuntimeResource Prepare；成功 journal 保留到 delete，作为恢复权威；
6. 失败时先持久化整体 `ROLLING_BACK`，对相反顺序的每一步同样采用 undo-INTENT-before-write、
   readback、RESTORED-after-write；全部恢复后 unlink journal并 fsync parent；任一异值或恢复
   失败保持 `DEGRADED`，禁止 RuntimeResource/TAP/VM 和后续 Create，由 scanner 重放。

恢复决策是封闭表，不允许实现自行选择“继续或 rollback”：

| lifecycle/create | server/epoch | 唯一动作 |
|---|---|---|
| PREPARED/SERVER_IDENTIFIED/SOCKET_READY | helper 原身份仍活且未超时 | watchdog 只观察；此时不允许存在 controller WAL |
| PREPARED/SERVER_IDENTIFIED/SOCKET_READY | helper 死亡或 30 秒超时 | scanner revoke 新 epoch，durable handoff 两 owner，cleanup-only |
| CONTAINERD_COMMITTED + IN_PROGRESS | immutable+containment 匹配、server 持当前 E | server 按 controller readback forward；`CONTROLLERS_COMMITTED` 后才按 RuntimeResource INTENT forward |
| CONTAINERD_COMMITTED + SUCCEEDED | server 持当前 E | 只做 controller/resource exact readback；不再 forward allocate；异值标记 terminal DEGRADED 并转 cleanup |
| CONTAINERD_COMMITTED + FAILED | 任意 | 永不 forward；按 failure-drained/30 秒规则 handoff 后 cleanup |
| 任一 pre-cleanup state | server 死亡、immutable mismatch 或 containment breach | scanner 以 E+1 revoke，durable handoff 两 owner，rollback/cleanup-only；immutable mismatch 不 signal，containment breach 按 4.4 signal |
| CLEANUP_REQUIRED/OWNERS_DURABLE/SERVER_STOPPED | 任意 | scanner 是唯一 owner；controller WAL 只反向 rollback，RuntimeResource INTENT 只 release/reconcile，禁止任何 allocate |
| 任一方向遇到 controller 实值既非 old 也非 target | 任意 | durable DEGRADED/quarantine；禁止 allocate、禁止猜写，持续报告并等待人工/后续策略 |

scanner 在 cleanup-only 模式按 INTENT/readback 反向恢复 controller；若 leaf 已精确为空且将被安全
删除，可以 durable 标记 `ABANDONED_FOR_EXACT_DELETE` 后由 HostCgroup owner 删除，不能把 journal
静默当作已 rollback。server 死亡会由内核释放 `operation.lock`；server 卡住时，scanner 先仅持
`record.lock` revoke E 并把已 durable 的 owner/INTENT handoff，进入
`CLEANUP_OWNERS_DURABLE` 后才 signal，随后取得 `operation.lock` 做 reconcile。因为 server 的
任何副作用都要求先持久化 INTENT 并复查 E，所以 handoff 与 signal 之间不会出现不可追踪分配。

测试在每次 journal temp-write/fsync/rename/parent-fsync、controller write/readback、step mark、
overall commit、rollback 与 unlink 前后注入 crash。identity、overhead 与
`CONTROLLERS_COMMITTED` 全部完成后，才允许 Cube-owned RuntimeResource Prepare、TAP 与 VM
分配；每项分配仍须先写 external RuntimeResource owner INTENT。containerd 的 CNI ADD 在
CreateSandbox 前已经可能完成，它归
containerd 所有；Cube 拒绝后必须由 containerd CNI DEL，验收只要求 Cube-owned 分配为零并
证明 CNI 回到基线。

### 5.4 Stop、Shutdown、delete 与双 owner handoff

- StopSandbox 停 Guest/VM，server 留在 leaf 完成响应；ShutdownSandbox 让 server 正常退出；
- delete action 使用 ServerIdentity 确认/终止准确 server；没有可验证 identity 时永不 signal；
- 任一 cleanup trigger 先在 `record.lock` 下 revoke operation-owner epoch并推进
  `CLEANUP_REQUIRED`，随后把 external `host-cgroup-owner.json` 与
  `runtime-resource-owner.json`（包括 EMPTY、未决 INTENT 和已分配 generation/handle）分别写入
  长期 scanner 的独立 durable queue：destination 临时写、file fsync、rename、parent fsync。
  两个 destination 都 readback 成功后才推进 `CLEANUP_OWNERS_DURABLE`；source 此时仍保留，
  只有 destination 完成 cleanup 并 durable ack 后才删除；不存在 per-delete reaper spawn；
- live server 只有在 `CLEANUP_OWNERS_DURABLE` 后才允许 graceful stop 或按 4.4 pidfd signal；
  原身份死亡后推进 `SERVER_STOPPED`。任一 handoff 失败时仍尝试另一个并聚合错误，但禁止 signal，
  scanner restart 后从 source/phase 重试；因此 bundle、server 或 containerd 先消失都不会丢掉
  RuntimeResource lease/generation；
- 两个 handoff、address/socket 清理和 sandbox resource 清理都必须尝试并聚合错误，一个
  owner 失败不得跳过另一个；各 reaper 只处理自己的 record；
- socket cleanup 使用 canonical record 的 path/dev/inode，identity 不匹配则不 unlink；bundle
  已消失不影响 scanner；scanner crash 由 systemd 重启后从 queue 继续；
- systemd unit/path 已消失、cgroupfs path 已不存在视为幂等成功；仍有 non-target PID 时不
  回收；
- containerd 重启且 Shim 存活时复用 server/scope并重新 readback；Shim crash 由 delete
  helper/reapers 收敛。节点重启的完整 reconcile 属于 S4，但 boot ID fencing 必须在本阶段
  生效。

## 6. 动态更新边界

Cube 不承诺跨 Host/Guest 的原子事务：kubelet、Cube leaf、Guest Agent 是三个 owner。

| 层 | 动态 resize 行为 | 失败/恢复边界 |
|---|---|---|
| kubelet Pod parent | kubelet 按自身顺序更新 | Cube 只读；以 controller readback 为证据 |
| Cube static leaf | 不变 | 创建期 transaction；不接收 workload aggregate update |
| Guest container | S3.4b Task Update | 目标容器 rollback/degraded/retry 契约不变 |

`UpdatePodSandboxResources` 未被 containerd local sandboxer 转发不阻塞父层 enforcement。
S3.4b 极端 unchecked memory decrease 继续由 `K8S-OQ-017` 跟踪。VM 不支持 hotplug，首版只
验收 resize 后 aggregate 不超过创建时预留 `cube.vmmres` 的场景；超过静态容量不伪装支持，
由 `K8S-OQ-018` 跟踪。

## 9. 明确不伪装支持的边界

  `memory.events max 0→39`、`oom 0→1`、`oom_kill 0→3`、`oom_group_kill 0→1`。

  `OOMKilled/137`，同 Pod survivor 身份稳定且 HTTP `3/3`。此外

  `inv-v86i55g64g` 使用精确 `cgroup.kill` 令其 scope inactive 且 cgroup 消失；真实

## 失败尝试边界与后续项

- `inv-386htsg4mg` 以默认/64Mi 工作负载规格并发创建 8 个启动即 OOM Pod，VM 启动阶段
  反复进入 `ReleasePending`。该轮没有采集到足以归因 Host OOM 的 `memory.events`，因此只
  记录为小容量/高并发启动边界 `K8S-OQ-021`，不把猜测写成结论；改用显式 2-vCPU/1GiB
  VM 后由 `inv-886i0qgtq9` 通过 notifier 目标验证。
- inactive scope 首轮 `inv-386i2f0e32` 中 `systemctl kill` 因 PVM 辅助进程返回
  `EINVAL`，但 scope 已被清空；后续 Kubernetes 删除仍成功。正式回归改为精确
  `cgroup.kill`，由上述 `inv-v86i55g64g`/`inv-b86i5egc5x` 通过。
- `inv-886i9h01p9` 的长 exec + resize 超时按 `K8S-OQ-022` 跟踪；该轮只证明异常后的
  scanner 收敛，不证明并发更新成功。
- 若干探索脚本因 label 假设或本机 `crictl` 不支持参数而在执行断言前失败，未形成集群
  写入或验收结论；所有测试对象最终均进入 exact baseline。

## 候选结论

S3.4c.4 在最终 `2a23aa3c` 上覆盖六 Pod/九容器可独立审计的 QoS 与三层数值、Host
CPU/PIDs、Guest 正常期和启动阶段定向 OOM、survivor 隔离、containerd restart、inactive
scope 删除和双节点 exact baseline。Host memory ceiling 与容量内 resize 的已通过证据来自
资源路径相同的上一候选，最终提交只修改 OOM notifier 和 scope cleanup，并由本轮对应定向
回归加固。`K8S-OQ-014`、`K8S-OQ-020` 已具备关闭证据；小 VM 高并发启动和长 exec +
resize 组合分别登记为 `K8S-OQ-021`、`K8S-OQ-022`，进入 S3.4d，不冒充已通过项。

# S3.4b Guest per-container cgroup 设计冻结

状态：`FROZEN`；同一 reviewer 已于 2026-08-31 给出 `APPROVE S3.4b DESIGN`。

## 目标与边界

S3.4b 只修复 Cube Guest 内每个容器的 resource parent cgroup；Host Pod VM 包络留给 S3.4c。目标是让 OCI create 与 `Task.Update` 对同一字段使用同一协议、同一数值转换和同一错误语义，并保证不能执行的请求明确失败，不再返回 accepted-unapplied。

首版实现固定为 Linux cgroup v2。旧 Cubebox 请求仍可走现有 protobuf 兼容路径；Kubernetes sandbox 必须协商 `io.cubesandbox.agent.container.resources-v2>=1`，缺失或版本不兼容时在启动 sandbox 时 fail-closed。

## 协议

在 Shim 与 Agent 两份 `oci.proto` 的 `LinuxResources` 增加相同 wire tag 的 `LinuxResourcesV2 resourceV2 = 8`：

```protobuf
message LinuxResourcesV2 {
    uint32 version = 1;
    string mediaType = 2;
    bytes value = 3;
}
```

- `version` 首版只接受 `1`。
- `mediaType` 固定为 `application/vnd.cubesandbox.oci.linux-resources.v1+json`。
- `value` 是经严格 schema 校验后重新编码的单个 OCI `linux.resources` JSON object，上限 256 KiB；对象 key 稳定排序，保留 scalar presence、空值与 `unified` map。Shim 必须在构造任何 `serde_json::Value`、map 或 typed OCI 对象之前，分别对 create 的原始 `config.json` bytes 和 `UpdateTaskRequest.resources.value` bytes 运行 streaming raw parser：任意对象层（包括 `unified`）出现重复 key 都拒绝，所有对象层都按该入口的 schema allowlist 拒绝 unknown field。只有 raw 校验通过后才允许生成 `Value`、typed OCI 和 canonical V2 payload，防止重复 map key 被覆盖或 unknown field 被 typed 反序列化丢弃。Agent 对收到的 canonical payload 再用同等严格、拒绝任意层 duplicate/unknown key 的独立 parser 复核。
- 只有 Kubernetes managed sandbox 发 V2：create 和 update 都携带信封，旧字段同时生成，仅用于 wire 向后兼容与已有 device 安全通道；Agent 看到 V2 后以 V2 controller 字段为准。legacy Cubebox 永远只发旧字段，避免在未协商路径上误用新 wire。
- V2 payload 不允许携带 `devices`。create 的 device 规则继续经过 S3.3 已验收的 Host Shim 清洗和 privileged 双门禁，再从旧 protobuf 合入；update 若请求 device 变化则明确拒绝。
- Agent 独立校验 version、media type、大小、JSON object、duplicate/unknown key、禁止字段和每个值，不能只信任 Shim。新 Agent 广告上述 capability；Kubernetes sandbox 同时要求 lifecycle 与 resources-v2 capability，任一 capability 缺失或版本不兼容都必须在首个 Task 之前销毁 sandbox 并恢复基线。

选择版本化信封而不是直接给旧 proto3 scalar 增加默认值约定，是为了保留 `absent`、`0`、`false` 和空字符串的区别；新增 wire tag 对旧 Agent 向后兼容，capability gate 则防止新 Shim 与旧 Agent 静默降级。

## 字段矩阵

| OCI 字段 | create/update 行为 | cgroup v2 目标/规则 |
|---|---|---|
| `cpu.shares` | 支持 | absent 或显式 `0` 都表示 unset：create 不写、update 保持 controller 与已保存 spec 不变；其他值严格复刻 containerd/cgroups v3.1.3 的转换和边界夹取，绝不写非法 `cpu.weight=0`；覆盖 `1/2/51/102/204/512/1024/262144/262145` |
| `cpu.quota` / `cpu.period` | 支持，presence 独立 | quota absent 保持当前，`-1→max`，`>=1000` 原值，`0..999` 或 `<-1` 拒绝；period absent 保持当前，合法范围固定为 kernel 的 `1000..=1000000` 微秒，`0`/越界拒绝。二者与当前另一半合成一次 `cpu.max` 写入；create 当前值是 kernel 默认 `max 100000`，验收覆盖非默认 period create/update |
| `cpu.cpus` / `cpu.mems` | 支持 | absent 或显式空字符串都表示 unset/no-op：create 继承、update 保持 controller 与已保存 spec 不变；非空值先校验格式和父层 effective 集合，先写 `cpuset.mems` 再写 `cpuset.cpus` |
| `cpu.idle` / `cpu.burst` / realtime | 首版明确拒绝 | 不允许静默丢弃；后续需单独 capability 和现场矩阵 |
| `memory.limit` | 支持 | absent 不写，`-1→memory.max=max`，`>=0` 原值，`<-1` 拒绝；显式 `0` 保持为 `0`，并可能使后续 create 无法加入进程 |
| `memory.reservation` | 支持 | absent 不写，`-1→memory.low=max`，`>=0` 原值，`<-1` 拒绝；显式 `0` 用于清除 soft protection |
| `memory.swap` | 支持 | absent 不写；`-1→memory.swap.max=max`；`>=0` 是 OCI memory+swap 总量，使用本次 limit，否则读取当前 `memory.max`。有效 memory 为有限非负值时要求 total>=memory 并写差值（可为 `0`）；有效 memory 为 `max` 时只接受 swap `-1`，有限 total 拒绝；`<-1` 拒绝 |
| `memory.swappiness`、kernel、kernelTCP、disableOOMKiller、useHierarchy | cgroup v2 首版明确拒绝 | 不再把默认 `swappiness=0` 写成 `memory.swap.max=0` |
| `memory.checkBeforeUpdate` | 支持 `true/false` presence | 仅影响 update：`true` 且本次有有限目标 limit 时，在任何写入前比较 `memory.current` 并在 current>target 时拒绝；`true` 但没有目标 limit 是无动作；`false`/absent 不做 userspace precheck，kernel reclaim/OOM 副作用不属于 controller rollback 可逆范围 |
| `pids.limit` | 支持 | `-1→pids.max=max`，`>=0` 原值（`0` 不改写为 `max`），`<-1` 拒绝；create 的 `0` 预期阻止 init task 加入并触发显式 create cleanup |
| `hugepageLimits` | 支持 | 按 OCI base-1024 规则把 `KB/MB/GB` 规范化成 kernel 文件名后写 `hugetlb.<size>.max`；同一请求中规范化到同一文件且值相同则合并，值冲突则写前拒绝；文件不存在或值不合法时写前失败，`limit=0` 有效 |
| unified `memory.swap.max` | 白名单支持 | 接受非负整数或 `max`；与 typed swap 同时存在时目标值必须一致；Kubernetes NoSwap 回归必须证明该 key 真正进入 Agent |
| unified `memory.oom.group` | 白名单支持 | 只接受 `0` 或 `1` |
| 其他 unified / invalid key | 明确拒绝 | 返回字段名和不支持原因，零 controller 变化 |
| devices | create 复用 S3.3 通道；update 拒绝 | V2 payload 禁止，防止绕过 privileged/device 清洗 |
| block I/O、network、RDMA | 首版明确拒绝 | 当前 Guest 执行器没有完成 cgroup v2 等价性与回滚验证，不得 accepted-unapplied |

shares 映射以固定依赖的上游实现为准：<https://github.com/containerd/cgroups/blob/v3.1.3/cgroup2/utils.go#L138-L164>。PIDs、memory 与 CPU 字段定义以 OCI runtime-spec v1.2.1 为准：<https://github.com/opencontainers/runtime-spec/blob/v1.2.1/config-linux.md>。

## 保存状态与 partial update

Agent 的内部 OCI 类型补齐 V2 能接收的 `idle`、`burst`、`useHierarchy`、`checkBeforeUpdate` 和 `unified` presence；前四项即使首版拒绝，也不能在 decode 时静默消失。V2 payload 的 canonical bytes/version 同时保存在 container config 中，供诊断和未来恢复使用。

update 只在 transaction commit 后做逐字段 merge，禁止当前代码的 CPU/memory 整对象替换：

- CPU/memory 的 absent 字段保留旧值；shares `0`、cpus/mems 空字符串按上表 no-op，不覆盖旧值；显式 `false`、`0` 和 `-1` 仍按各自 presence 保存。
- `pids` presence 替换 limit；hugepage 按规范化 page size 合并；同 size 新值覆盖旧值，未出现的 size 保留。
- `unified` 按 key 合并，未出现的 key 保留。typed 与 unified 若落到同一文件，planner 基于本次输入和当前 controller 计算唯一目标；同一请求目标不一致则写前拒绝。
- planner 永远从当前 controller 读取未指定的 `cpu.max` 另一半和 swap 转换所需的当前 `memory.max`，不从可能滞后的保存 spec 推断实际值。
- 任何 decode、validation、transaction 或 rollback-success failure 都不修改 canonical payload、内部 OCI spec 或 container config。

## 发包与兼容矩阵

| 调用路径 | Shim 发包 | Agent 行为 | 验收 |
|---|---|---|---|
| Kubernetes managed sandbox，新 Shim + V2 Agent | sandbox 启动先要求 lifecycle>=1、resources-v2>=1；Task 同时发 legacy+V2 | 必须严格解析 V2，controller 以 V2 为准，device 只取清洗后的 legacy | 正常 create/update 全矩阵 |
| Kubernetes managed sandbox，新 Shim + 无 capability/版本错误 Agent | 不允许创建首个 Task | Host Shim fail-closed 并删除 sandbox/VM/lease | 两类 capability-negative exact baseline |
| legacy Cubebox，新 Shim + 任意 Agent | 只发 legacy，不附 V2 | 维持原 legacy parser | legacy-only create/update 回归 |
| 旧 Shim + 新 V2 Agent | 只有 legacy | 没有 V2 时维持原 legacy parser | wire 向后兼容回归 |

新 Shim 不在未协商路径发送 V2；因此不存在“旧 Agent 忽略 tag 8 后继续运行”的 Kubernetes 静默降级。Agent 收到 V2 时不允许 fallback：版本、media type 或 JSON 错误直接拒绝。

## Agent 执行与原子性

在 Agent 内新增独立的 cgroup v2 resource transaction 模块，不把新语义继续堆进旧 `set_resource!` 宏：

1. 解码 V2 payload，并完成全部 sentinel/range、交叉字段、重复/unknown key、controller 文件和 cpuset parent-effective 校验。
2. 把同一文件的 typed/unified 输入归并成唯一目标；冲突在写入前失败。
3. 在任何写入前读取全部目标文件的原值。读不到任一文件即失败，且不产生写入。
4. 按 `cpuset.mems`、`cpuset.cpus`、CPU、memory/swap、PIDs、hugetlb、unified 的确定顺序写入；`cpu.max` 始终一次写 quota+period。
5. 写完逐项读回并与规范化目标比较。写入或读回失败时按逆序恢复所有已触碰文件，再读回旧值；错误同时报告原始失败和 rollback 结果。undo journal 在首个写入前原子落到 container bundle，commit 或完整 rollback 后删除。
6. 只有 transaction commit 后才更新 Agent 保存的 OCI spec。validation/preflight failure 保证零 controller 写入；运行期 failure 且 rollback/readback 全部成功时，保证旧 controller 与旧 spec 恢复。

rollback 自身失败时不能伪装成原子失败：container 进入 `ResourceDegraded` fail-stop 状态并保留 undo journal、原错误、rollback 错误和当前读数。Agent 当前以 sandbox mutex 串行化同一 sandbox 的 update/delete/stats；S3.4b 在此边界上规定：

- 后续 update 不接受新目标，只先重放 undo；恢复成功后清除 degraded 并返回“已恢复，请重试”，下一次 update 才能执行新请求；恢复仍失败则保持 degraded。
- start/exec/stats 明确返回 failed-precondition，signal/wait 保留用于终止，RemoveContainer 始终允许并负责清理。
- delete 等待正在执行的 transaction 完成，再杀进程、清理 bundle/journal 和 cgroup；成功后 degraded 状态随 container 一起删除，失败返回聚合 cleanup 错误并保留可重试 owner。
- controller 原子保证不覆盖 Agent 进程崩溃、节点掉电，也不能撤销 `checkBeforeUpdate=false/absent` 时 kernel 已产生的 reclaim/OOM/进程死亡；journal 为 S4 reconcile 留证，但崩溃恢复不在 S3.4b 冒充完成。

create 需要新增显式 owner cleanup，不能依赖当前并不存在的隐式回滚。`do_create_container` 从登记 storage/bundle 开始持有 `PendingCreate`，它拥有 storage refs、bundle/rootfs、局部 `LinuxContainer`、runtime process leaf 和 resource parent。只有 `ctr.start()`、shared PID namespace 更新和 Sandbox 插入全部成功后才转移 ownership。任一步失败都调用幂等 `abort_create`：杀死已知/所属 cgroup PID、卸载 rootfs、删除 bundle、先删 process leaf 再删 parent、释放 bind watcher/storage refs并逐项验证。cleanup 失败时将 owner 留在 Sandbox `pending_creates`，同 ID create 被拒绝，RemoveContainer 可继续清理；RPC 同时返回原失败与 cleanup 状态，不能声称 exact cleanup。

事务 I/O 抽象必须可注入，单元测试覆盖：预检失败零写入、中途第 N 次写失败、读回不匹配、逆序恢复成功、rollback 自身失败进入 degraded、重放 undo 恢复，以及 update/delete/stats 串行状态机。云端 root integration test 在真实 cgroup 上包裹实际文件 I/O 注入第 N 次写入/读回失败，分别验证 controller、spec、journal 和重试结果；不能只用写前非法请求替代中途失败。

## 代码组织

- `CubeShim/shim/src/container/resources.rs`：Shim 侧 streaming raw JSON duplicate/逐层 allowlist 校验、字段策略、canonical JSON、V2 envelope 和 update device fail-close；create `config.json` 与 raw `UpdateTaskRequest.resources.value` 必须先经这里校验，才可进入任何 `Value`/map/typed OCI 反序列化。
- `CubeShim/protoc/protos/oci.proto` 与 `agent/libs/protocols/protos/oci.proto`：只增加兼容 wire tag/message；生成文件由各自 build script 产生，不手工维护行为。
- `agent/rustjail/src/resources.rs`：严格 V2 envelope 解码、legacy device 合并、逐字段 merge 和内部 OCI presence 模型。
- `agent/rustjail/src/cgroups/fs/resources_v2.rs`：cgroup v2 规划、转换、事务写入、读回与 rollback。
- `agent/src/rpc.rs` / `agent/rustjail/src/container.rs`：`PendingCreate` ownership、`ResourceDegraded` 状态机和同 sandbox RPC 串行边界。
- 旧转换和 cgroup v1 路径保留给非 Kubernetes 的 legacy Cubebox；V2 请求在非 unified cgroup 节点明确失败。

## 验收矩阵

本地验收必须包含 Shim/Agent protobuf wire round-trip、presence、字段拒绝、全部 sentinel/range、shares 固定向量、swap 转换、hugepage 同义/冲突、cpuset empty、逐字段 merge、transaction/rollback/degraded/PendingCreate 单测，以及两侧全量 `cargo test`/`clippy` 和生成文件一致性。严格 JSON 必须分别从 raw create `config.json` 和 raw update `UpdateTaskRequest.resources.value` 入口覆盖 nested unknown、重复结构字段及重复 `unified` key；每个拒绝用例都断言未调用 Agent 且 controller/spec 零变化，并覆盖 Agent 对 canonical payload 的第二道同类拒绝。

云端在项目 CVM 上使用同一 OCI 输入做 runc/Cube 对照，至少覆盖：

- CPU shares `0/1/2/51/102/204/512/1024/262144/262145`，quota `-1/0/999/1000/<-1` 与 period `0/999/1000/非默认/1000000/1000001` 的独立 create/update；
- memory limit/reservation/swap 的 absent、`0`、`-1`、`<-1`、finite/current-max 组合；limit-only 在非零 swap 基线上的 create/update、`checkBeforeUpdate` 三态和 Kubernetes NoSwap；
- cpuset cpus+mems 的 absent/empty/合法/越界、PIDs `0/-1/<-1`、2Mi/1Gi hugepage 的存在/不存在/同义重复/冲突路径；
- `memory.oom.group`、两个 unified key 冲突、未知/非法 unified；
- 多字段成功 update、写前非法多字段 update、真实 cgroup 第 N 次写/读回失败及 degraded→undo 重试、连续 partial update、同 Pod survivor、压力/OOM/PIDs 正反例；
- `pids.limit=0` 使 cgroup 已建且资源已写后 init 加入失败的 `PendingCreate` exact cleanup，以及显式 cleanup-failure 可重试 owner；
- capability 缺失/版本错误在首个 Task 前失败、legacy-only 与 V2 wire 组合；
- create/update/delete 失败后的 Pod、Task、Sandbox、VM、lease、mount、bundle/journal/pending owner、cgroup 与服务健康 exact baseline。

正式矩阵和独立 audit 通过后，仍由 S3.4a 的同一 reviewer 给出 `APPROVE S3.4b DONE`；未获批准前不进入 S3.4c。
